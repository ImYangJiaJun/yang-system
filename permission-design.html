设计方案 · 评审稿 v1 · 2026-10-05

权限配置可视化：从「打字符串」到「勾选工作台」

现状的权限管理面要求操作者输入用户数字 ID 与权限字符串（如 access.grants.read），对业务同事不可用。
本方案不改变任何权限模型（目录 / 直授 / 组 / 版本传播全部保留），只重做表达层，并补两个只读接口。

1 · 现状：为什么业务同事用不了

现在权限配置分布在两个页面，全部基于通用表单引擎，输入的粒度和人的心智模型完全脱节：

现状对业务同事的问题
「目标用户」是数字 ID 输入框（直授页的查询条件条 / 授予对话框）同事不知道任何人的数字 ID，只认识名字 / 花名 / 手机号
「权限」是纯字符串文本框，如 access.grants.read看不懂、记不住、易拼错；填错目录外字符串直接被 400 拒（fail-closed 是安全特性，但交互零提示）
过期时间是 Unix 秒整数无法理解「1700000000」是何时
权限组页成员是 「用户 #7」这样的数字不知道是谁；加成员同样要输入用户 ID
没有「这个人到底能干什么」的总览直授一页、组一页、有效权限（并集）只存在于签发快照里，任何界面都答不了这个最常见的问题
没有「谁能用这个功能」的反查业务提需求「给运营开 XX 功能」，管理员只能逐个翻组、翻用户
管理员等价权限、孤儿条目虽有数据，但展示为普通文本危险授出去没感觉；失效条目不知道什么意思
▍现状：一次直授对话
目标用户 请输入数字 ID…
权限 access.xxx.yyy 必须逐字手打
过期时间 Unix 秒（留空永久）
提交（可能 400）
▍方案：同一次直授
🔍 搜索用户… 王小明 PM · 产品部
+ 添加权限…（从目录勾选）
🗓 2026-12-31 到期后自动失效
提交授权

2 · 设计原则

  1. 人话优先：每个权限有中文名 + 所属功能分组 + 一句「能干什么」。中文名不需要后端改——UI 目录里的 Action 自带 title / description，用目录的 declared_by 即可映射出分组与说明。
  2. 三个自然视角，一次只回答一个问题：按人（ta 有什么权限）、按功能（谁能用这个）、按组（角色怎么配）。
  3. 勾选代替打字：所有权限位从目录里选，键盘只用于搜索。选择器与「授权」是同一件事的三处入口。
  4. 危险可见：管理员等价权限（红）、孤儿条目（琥珀）、过期（灰/琥珀）全部徽标化并给出处置出路。
  5. 模型零改动：目录、直授、组、Outbox 版本传播、G2 闸门、最后管理员不变量——全都不动。所有安全约束天然继承，本方案不引入新的授权路径。

3 · 方案总览：权限工作台（Permission Workspace）

把现有的「权限管理」「权限组」两个平铺页面，升级为一个左侧三个入口的工作台。三个视图共用同一套组件（用户选择器、目录选择弹窗、徽标），数据全部来自现有接口 + 一个新增只读接口：

按用户：搜索一个人 → 看 ta 的全部权限

  • 顶部全局搜索：名字 / 花名 / 手机号，下拉候选带头像与部门。
  • 用户权限总览三块：直授权限（分组勾选态 + 过期标签）、所属权限组（卡片）、有效权限（直授 ∪ 组的只读并集，标注来源）——直接回答「这个人能用什么」。
  • 从总览上直接发起「授予 / 撤销」，无需离开页面。

↓ 完整示意见 §4

按功能：搜索一个功能 → 看谁能用、谁在用

  • 权限目录按模块分组的浏览 + 搜索（中文名 / 字符串都搜）。
  • 点开一条权限：基本信息（中文名、声明者、管理员等价警示）+ 两张持有者表：直授持有者（用户、授予人、时间、过期）、组持有者（组、成员数）。
  • 页内一个「授权」按钮：选用户或选组，直接授出。
数据前提：现有库表已有按 permission 反查的索引（idx_authz_grant_permission）与组条目查询，只缺一个把它暴露出来的只读 Action（P2，见 §8）。

↓ 完整示意见 §5

按组：角色卡——给「角色」配权限、把人拖进角色

  • 组列表卡片化：组名 + 描述 + 条目数 / 成员数 + 危险徽标 + 孤儿徽标。
  • 组详情：条目改为勾选式（目录选择弹窗多选）；成员改为用户选择器（名字搜索，不再有「用户 #7」）。
  • 内置全权组只读展示：锁图标 + 「权限由权限目录实时计算」，条目 = 全目录。

↓ 完整示意见 §6

7 · 关键交互细节

目录选择弹窗（三处共用，替代所有权限文本输入）

  • 搜索框：中文名、权限字符串、模块名都搜。
  • 按 declared_by 的模块分组折叠（「审批与工作流」「账号与安全」…），每组显示声明者。
  • 管理员等价权限：红字 + 徽标；选中即出现红色警示条（图见 §4 弹窗）；提交按钮在含管理员等价选择时需二次确认。
  • 找不到目标权限时显示空态引导：「该功能可能未启用或你无查看权限」，而不是让用户自己发明字符串。

过期时间

  • 日期控件（非 Unix 秒），可选「永久」；展示侧给相对文案（「7 天后过期」「已过期」）。

生效提示

  • 所有写操作成功后 toast：「已授权，对方刷新会话后生效」——与现有版本传播语义一致，不承诺即时生效。

徽标语义

徽标含义出路
⚠ 管理员等价授予 = 交出部分系统管理能力（理由由代码侧清单提供）仅系统管理员可授；界面给出拒绝理由文案
已失效孤儿条目：权限已不在目录中，不参与解析可移除（沿用现有 remove_item 语义，不自动清理）
N 天后过期 / 已过期直授过期状态（expired 派生标记已有）行内一键「续期」
来自 XX 组有效权限并集的来源标注点击跳转该组详情

空态

  • 用户无任何权限：引导「授予第一条权限或加入一个权限组」。
  • 组无条目：引导「添加条目」；全权组不显示该引导（只读）。

8 · 后端配合清单（最小改动）

原则：权限模型与全部写接口零改动，只补「表达层缺的数据」。已核对的现状：UI 目录含全部 Action 的 title/description 与模块信息，PermissionEntry 已含 admin_equivalent 与 declared_by。

需要的数据现状方案
用户选择器（名字 / 搜索） account.users.list_users 已存在（需核对权限位与可见性）；组详情成员目前只回 user_id 数字 P0 纯前端：前端拉一次用户列表做 id→名字映射（名字数据量小）。若 list_users 权限位过严，新增轻量只读 Action（authenticated-only，只回 id + 名字 + 启用态），专供权限工作台
权限中文名 / 分组 目录里 Action 自带 title，权限条目带 declared_by 零后端改动：前端由 declared_by → 对应 Action → 中文名与模块分组；映射不到时回退显示字符串本身
「谁能用 X」反查（视图二） 表已有 idx_authz_grant_permission 反查索引与组条目查询，无对外接口 P2 新增一个只读 Action（如 access.grants.list_holders：permission → 直授持有者 + 组持有者），复用现有 repository 查询，无写路径
管理员等价理由文案 理由在代码侧清单 ADMIN_EQUIVALENT_PERMISSIONS，403 已用它；目录接口未回 reason 字段 P0 前端内置同一份映射（3 条，静态）；或后端在 PermissionEntry 序列化加 reason 字段（一行改动）——推荐后端加，避免双份清单漂移
直授审计字段（授予人 / 时间 / 过期） list_user_grants 已返回 granted_by / occurred_at / expired 零改动，前端直接画
不要做的事：不加角色模型、不加权限通配符、不加运行期注册权限、不改 G2 闸门与最后管理员不变量——这些是当前 fail-closed 安全面的根基，本方案只重做「人怎么操作」，不重做「系统怎么判」。

9 · 分期落地

期范围验收标准
P0 纯前端，不动后端：
  • 目录选择弹窗（替换三处权限文本输入）
  • 权限中文名 / 模块分组映射
  • 组页成员名字显示 + 用户选择器
  • 过期日期控件、徽标（危险 / 孤儿 / 过期）、生效提示、空态
 业务同事可在无后端变更下完成一次完整授权：搜索名字 → 勾选功能 → 选过期时间 → 提交；全程无数字 ID、无字符串输入
P1 视图一「按用户」：用户权限总览（直授 + 组 + 有效权限并集）+ 页内授 / 撤 / 续期 打开任意用户，可一眼回答「ta 有哪些直授、在哪些组、有效权限是什么」，并可原地授权
P2 视图二「按功能」：目录分组浏览 + 持有者反查（新增 list_holders 只读 Action）+ 审计时间线 回答「谁能用 X 功能」并可从此页直接发起授权；反查结果与直授 / 组两页一致（同一数据源）

10 · 取舍与风险

取舍 / 风险处理
「有效权限」并集是界面计算口径，≠ 当前 Token 快照明确标注「刷新会话后生效」；如需实时权威口径，P2 可选后端补 effective snapshot 只读 Action（与签发解析同一代码路径，保证口径一致）
用户量大时搜索性能复用 list_users 分页 + 服务端过滤；名字映射一次缓存（staleTime 与现有查询一致）
权限条目多时分组树高度折叠 + 搜索过滤，展开默认收起；按模块分组天然限高
名字 / 用户列表可见性权限工作台本身已限访问者（目录门控），风险与现有组页一致；不新增全局用户导出
前端内置管理员等价理由（P0 过渡）可能漂移P0 即推荐后端在目录接口回 reason（一行改动），避免双份清单；测试用冻结目录钉住
不改模型 = 界面能看到、但授不出去的组合G2 闸门 / 最后管理员等约束在提交时返回 403 中文理由（现有错误文案已可读），弹窗内提示 + 二次确认缓解

11 · 实现方案（2026-10-05 已批准，三视图一次性落地）

基于代码现状核实的落地方案：权限模型零改动，所有写操作复用现有 Action（grant_permission / revoke_permission / 组 9 Action，G2 闸门、自提权、最后管理员不变量天然继承）。

后端改动（3 个只读 Action + 1 个字段，无写路径）

改动内容位置 / 契约
① account.users.lookup 用户选择器数据源。authenticated-only（不挂 account.users.read——工作台可见者不一定有它），只回 id / username / email / status，q 为空时正常分页不过滤（前端据此循环翻页构建全量目录），上限 50 条防 DoS src/addon/account/user/actions/lookup.rs + UserRepository::search
② access.grants.list_holders 「谁能用 X」反查。权限位 ["access.grants.read"]，只读事务；直授持有者含过期行 + expired 派生标记，组持有者带成员数。复用 idx_authz_grant_permission 反查索引 src/addon/access/grants/actions/list_holders.rs + GrantRepository::list_by_permission_in_tx + GroupRepository::list_groups_holding_item_in_tx
响应：{direct:[{user_id,granted_by,occurred_at,expires_at,expired}], groups:[{id,group_key,title,member_count}]}
③ PermissionEntry.reason 管理员等价权限的中文理由随目录接口返回（避免前端双份清单漂移），null = 非管理员等价；测试用冻结目录钉住 src/addon/access/domain/permission_catalog.rs，理由取 sensitive_permissions 清单

前端改动

件内容
数据层 features/access/workspace-api.tslistUserLookup / useUserDirectory（循环翻页 id→名字 Map）/ listUserGrants（复用现有接口）/ listHolders / usePermissionMeta（目录 + UI 目录 → 中文名 / 模块分组映射，命不中回退字符串）
共享组件 features/access/components/UserPicker（lookup 搜索下拉）、PermissionPickerDialog（搜索 + 模块分组折叠 + 危险红条二次确认 + 过期日期控件，视图三无过期）、PermissionBadge（危险 / 孤儿 / 过期 / 来源）
三视图 PermissionWorkspacePage按用户（总览：直授分组 + 组卡片 + 有效权限并集；行内撤 / 重新授予）、按功能（目录浏览 + 持有者两张表 + 页内授权）、按组（现有 PermissionGroupsPage 原地升级：条目勾选 + 成员用户选择器 + 名字显示 + 内置锁）；全程无数字 ID、无权限字符串输入

验证与验收

  • 后端：新 Action 单测（参数契约 / 投影）+ 集成测试（lookup authenticated-only、list_holders 权限门禁与数据正确性）；前端：三视图垂直切片（对齐 module-page-access-grants.test.tsx 的 mock-fetch 模式）+ permission-meta 单测。
  • 验收标准：业务同事不接触 ID 与权限字符串即可完成——查一个人看权限、查一个功能看谁能用、给角色配权限加人；危险权限全程可见带理由。

落地顺序
