# V3｜详情页行为

**要回答**：展示**已提交**单据时，外部选项控件是**重新调接口**，还是用**提交时的快照**？

**为什么决定性**：官方已确认提交存的是 `options.id`。若详情页重新调接口，而旧汇率 id 已被补集停用
（读端按 `enabled` 过滤）→ **详情页显示空**。而「让旧 id 可解析」与「选项集不无限增长」互相冲突（详见设计文档 §6-V3）。

## 前置

**必须先有一个配了外部选项的控件**——今天没有（实测 13 张审批定义全部 `hasurl=False`）。
所以 V3 只能在 **T8（飞书侧配置）之后**做。但下面的 V3-0 可以**提前**验证另一件事。

- [ ] **V3-0｜先验公网可达（P-1 的冒烟测试，可提前做）**
      官方明文：「如果审批表单处于编辑状态，当数据源来自外部系统的控件时，**点击校验数据**或用户发起请求时，
      审批系统将对用户配置的外部数据源接口地址发起请求。」
      → 在副本里拖一个**临时单选控件**，配成外部选项，URL 指向我们的端点，点**「校验数据」**。
      → 服务端日志里出现请求 = **公网链路通**（P-1 关闭）；没出现 = 看飞书侧报错文案（多半是「HTTP 请求 URL 被封禁」）。
      **这一步不需要拉取跑通、不需要选项数据，只要端点能被调到。**

## 方法 A：看日志（最干净的判据）

- [ ] **V3-A1** 配好币种/汇率的外部选项（T8 完成）。
- [ ] **V3-A2** 记录服务端日志的基线（或直接 `tail -f`）。
- [ ] **V3-A3** 提交一单（用副本表单）。
- [ ] **V3-A4** 让日志静置 30 秒（确认提交动作本身已产生的请求都过去了）。
- [ ] **V3-A5** **打开该单据的详情页**。
- [ ] **V3-A6** 看日志里有没有**新的** `POST /api/v1/feishu/approval/options/payment_currency`（或 `payment_fx_rate`）：

      | 日志 | 判定 |
      |---|---|
      | 有 | **重新调接口** → 走方法 B 确认严重程度 |
      | 没有 | **用快照** → 「历史单据显示旧汇率」自动成立 ✓ |

## 方法 B：改数据后看显示（更强，同时验证机制冲突）

- [ ] **V3-B1** 提交一单，记下当时选的**汇率值 V1**。
- [ ] **V3-B2** 走完审批，记下单据 code。
- [ ] **V3-B3** 在台账表里**把汇率改成 V2**（或加一个新值，让 V1 在下一轮补集停用中被停用）。
- [ ] **V3-B4** 等一轮拉取生效（确认 `last_success_at` 前进、`feishu_option` 里 V1 已 `enabled=false`）。
- [ ] **V3-B5** 打开那张单据的详情页：

      | 显示 | 判定 | 含义 |
      |---|---|---|
      | **V1**（旧汇率） | ✅ 快照 | A11「历史单据显示旧汇率」成立，**V3 关闭** |
      | **V2**（新汇率） | ⚠️ 重新调接口 | 显示的不是提交时的值——**业务上要确认能否接受** |
      | **空** | ❌ 重新调接口且旧 id 解析不到 | **设计文档 §6-V3 的机制冲突成立**，必须专门解一次 |

- [ ] **V3-B6** 若出现「空」，按设计文档 §6-V3 的两个出口做决策：
      ① 停用与「不可解析」分离（停用只表示不出现在新选择里，但仍可被按 id 解析）；
      ② 或接受显示空，把汇率值另存到表单的普通字段里。
