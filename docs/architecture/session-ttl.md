# Access TTL 容量决策

## 当前决定

Access TTL 保持 `3600` 秒，Refresh TTL 保持 `2592000` 秒。本轮不把 Access TTL
缩短到 15、10 或 5 分钟。

这不是把 60 分钟声明为永久最优值，而是遵守容量边界：Refresh 会验证旧 Token、读取
MySQL 中同一授权快照、校验 `credential_version`、查询最新授权事实、原子消费旧 JTI，
再签发新 Access/Refresh Token。缩短 TTL 会按稳定会话数近似线性放大整条链路，不能只看
JWT 签名耗时。

## 本地可重复证据

基准使用真实 MySQL 8 与 Redis DB 15，建立 10 个会话；每个会话严格串行轮换 100 次，
避免并发复用旧 JTI 这一协议违规行为。三轮均为 1000/1000 成功：

| 轮次 | 吞吐量 req/s | p50 | p95 | p99 | 错误 |
|---|---:|---:|---:|---:|---:|
| 1 | 1026.36 | 9.085 ms | 11.032 ms | 12.643 ms | 0 |
| 2 | 1023.11 | 9.241 ms | 10.617 ms | 11.722 ms | 0 |
| 3 | 1108.80 | 8.650 ms | 9.910 ms | 10.771 ms | 0 |

原始记录见 [refresh-ttl.json](../../.ecc/benchmarks/refresh-ttl.json)，可执行测试见
`tests/refresh_load_benchmark.rs`。该数据覆盖应用 Action 派发、真实数据库和 Redis，
但不包含反向代理、跨主机网络、生产连接池竞争、复制、备份或邻近业务负载，不能外推为
生产容量承诺。

## TTL 对负载的确定性影响

若稳定活跃会话数不变，刷新频率近似为 `active_sessions / access_ttl_seconds`：

| Access TTL | 相对当前刷新负载 |
|---:|---:|
| 60 分钟 | 1 倍 |
| 15 分钟 | 4 倍 |
| 10 分钟 | 6 倍 |
| 5 分钟 | 12 倍 |

因此本地 p99 较低只证明当前路径没有明显单机延迟问题，不证明生产能够无条件承受 4–12
倍刷新量。目前缺少生产活跃会话数、连接池等待、Redis 容量、Refresh 失败率、重新登录率
和代理层 p99，缩短 TTL 的收益与代价尚不能真实量化。

## 后续调整门禁

仅在预发布环境取得以下证据后，才先灰度 15 分钟：

1. 使用生产等量活跃会话和代表性邻近流量运行基准，并通过
   `YANG_SYSTEM_REFRESH_P99_BUDGET_MS` 设置明确 p99 预算；
2. 记录 MySQL 连接池等待、事务延迟与查询 QPS，Redis JTI 消费/撤销写 QPS、内存和错误率；
3. 经真实 HTTPS 反向代理测量客户端并发刷新去重、Refresh 失败率和重新登录率；
4. 设置按错误率、p99、连接池等待和 Redis 故障率触发的配置回退阈值；
5. 15 分钟稳定经过观测窗口后，再以相同证据决定是否试验 10 或 5 分钟。

Redis 与 MySQL 都无法提供授权或凭据事实时继续 fail-closed；不能为了降低失败率把依赖故障
映射成 401，也不能绕过 JTI 单次消费或授权快照读取。
