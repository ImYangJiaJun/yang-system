# 静默失败与「摘除式」变异检验

**生成：** 2026-09-29　**范围：** 全仓库。来源是 xlsx 文件导入那条链（15 个任务、
45 个提交）的终审复盘。

## 规则

> **每处新增分支，至少做一次「摘除式」变异，并把输出留档。**

「摘除式」= 把新加的那一条判断/守卫/回写**删掉或反向**，重跑**聚焦**的那几条测试，
确认它们**变红**，然后改回来。（与「加一条断言」不是一回事：断言证明不了断言本身
被执行到。）

留档的最小形态：提交信息或任务记录里一行「变异：摘掉 X → 测试 Y 红（原话摘一句）」。
不做这一步，「覆盖」只是一个人的说法。

## 为什么这条在这条链上命中率极高

xlsx 导入那条链的 4 处计划代码错误里，**2 处是完全静默的**：

| 错误 | 为什么静默 | 怎么发现的 |
| --- | --- | --- |
| `row_number <= current_row`（本意 `<= header.header_row`） | 同一行第二个及以后的单元格被 continue 掉，**只剩每行的第一列能读到**。只勾一列的测试照样绿 | 变异检验 |
| `anomaly_by_label` 按**未 trim** 的文案建键 | 异常行回查不到自己的原因 → 静默保持 `enabled = true` 被喂给飞书，而回执里那条异常记录还在 | 变异检验 |
| Task 14 的桩判据写成 operation id（真实请求走的是路径） | 桩比真实服务端「宽容」，坏掉的消费方一直绿 | 变异检验 |
| Task 7 的「空测试」（夹具前提不成立，断言恒真） | 测试永远绿 | 变异检验 |

另有两处**只差一点也静默**：`read_snapshot` 的 `next_cell` 守卫（夹具的表头自己先
panic，删掉它全套测试仍然绿——2026-09-29 补了 `shared_strings_missing_data_row.xlsx`
才钉住）、`DateTimeIso` 被并进空串那一臂（日期列整列读成空，用户只看到「这一轮跳过了
它」）。

共同点：**错误的方向是「少做一点」而不是「报错」**。少做一点不会让任何断言变红，
除非那条断言是专门为它写的。

## 怎么做（最小成本版）

1. 写新代码时记下**它新增的每一个分支**（`if` / 守卫 / 提前返回 / 回执字段）。
2. 逐个删掉，只跑**相关的那几个**测试文件（`cargo test --lib --locked <前缀>` /
   `pnpm vitest run <文件>`），确认**恰好**是对应的那条变红。
   - 全绿 = 这条分支零覆盖，先补测试再继续。
   - 红了一片 = 说明它其实是承重分支，注释里写清「谁依赖它」。
3. 改回来，跑一遍完整门禁。

**别把变异当成「顺手也删点别的」**：一次只动一处，否则红的是哪一处说不清。

## 反例：什么样的测试不能算覆盖

- **夹具前提不成立**的测试（空测试）——先断言前提，再断言结论。
- **桩比真实服务端宽容**的测试——桩要么按请求参数回答（如按 `order_by` 排序后再分页），
  要么在收到没覆盖的请求时**抛错**（本仓库的 `stubFeishuApi` 就是这么做的）。
- **断言文案而不是行为**的测试——文案变了就红，行为坏了却绿。
