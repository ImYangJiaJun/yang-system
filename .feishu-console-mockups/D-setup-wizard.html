已知实现约束
  • 列表顶部的「全部 / 启用 / 停用」分段控件，服务端现在会拒绝：feishu_datasource.status 没有声明 .filterable(true)，框架对筛选是 fail-closed，会直接回「字段不允许筛选」。 要让它真的能用，后端需给该字段补 .filterable(true)（设计文档三处后端改动之外的第四处）。
  • 列表必须由前端显式传 order_by： list_datasources 没有默认排序兜底（list_options 有回退）， 不发排序条件就是无序分页，翻页会重复 / 漏行。
  • 没有任何 Action 能按 source_key 取单个数据源， 所以详情页头部要么再发一次带 where 的列表请求，要么靠导航态传递； 这个原型走的是导航态，刷新或分享链接会丢。
  • 「校验数据」按钮控制台做不到：唯一能校验的是 approval_options， 它要拿数据源 Token 自校验，而服务端只存 SHA-256 摘要，永远回不出明文 Token。 向导第 3 步因此把它标成「待后端补」。
  • 卡片 / 行上不能显示选项数量与最后同步时间（后端都不返回）。 要显示得给 list_datasources 加字段，或给 option 表补 updated_at select。
  • 列头没有排序箭头是故意的：title 只声明了 .searchable(true)（能搜、不能筛、不能排）， feishu_datasource 里只有 source_key 是 .sortable(true) 的。
  • 两边筛选能力不对称：详情页的选项列表可以按 enabled 筛 （option 表声明了 filterable），列表页的状态筛选不可以。所以这里没有给选项列表画筛选器。
  • 角色判断走 catalog.actions 里有没有对应 operation_id（目录本身已按身份投影），不需要前端解析 JWT。
  • 示例数据里的标识带连字符（原契约给的样例就是这么写的），但真实约束只允许 [a-z0-9_]——按真实规则，列表里那几条样例其实建不出来。 原型为了四个方案横向可比没有改样例，但新建的数据源一律用下划线形式， 别照着样例去推 URL 里的标识。
